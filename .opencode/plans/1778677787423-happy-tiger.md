# Expose `sade` instance for customization in `CliTransport`

## Goal

Allow consumers of `@tmcp/transport-cli` to extend the underlying `sade` instance with custom commands, options, version, examples, etc. — without forking the transport.

## Design Summary

- Accept a `setup` callback as a constructor option: `new CliTransport(server, { setup: (prog) => {...} })`.
- The callback receives the configured `sade` instance after built-in commands (`tools`, `schema`, `call`) and tool aliases have already been registered, but before parsing. This lets users add new commands, override existing ones, set `.version()`, `.describe()`, `.example()`, etc.
- Custom command **actions are invoked naturally**: after manual dispatch in `run()` fails to match a built-in or tool name, we invoke the `handler` returned by `prog.parse(..., { lazy: true })` for that custom command.
- Name collisions with built-ins or tool aliases are **allowed with a warning** printed to stderr at registration time (detected via snapshot/diff against `prog.tree`).

## Files to modify

### `packages/transport-cli/src/index.js`

1. **Type the new options object** with JSDoc:
   ```js
   /**
    * @typedef {object} CliTransportOptions
    * @property {(prog: import('sade').Sade) => void} [setup] - Hook to customize the sade instance.
    */
   ```
   (If `sade`'s type isn't directly importable, fall back to `any` for the `prog` parameter, mirroring the loose typing already used elsewhere — but prefer `import('sade').Sade` and verify in dev.)

2. **Constructor signature change** (backwards-compatible):
   ```js
   constructor(server, options = {}) {
       this.#server = server;
       this.#options = options;
   }
   ```
   Add private field `#options`.

3. **Inside `run()`**, after the existing tool-alias registration loop and before `prog.parse(...)`:
   - Snapshot known command names: `const known_names = new Set(Object.keys(prog.tree).filter(name => !name.startsWith('__')))`. This includes `tools`, `schema <tool>`, `call <tool> [input]`, plus tool aliases — note that sade stores them by the leading non-bracketed token (e.g. `'schema'`, not `'schema <tool>'`), based on the sade source. Validate by inspecting how the existing built-ins land in `prog.tree`.
   - Track tool alias names registered (the actual map keys), so we can also detect overrides of tool aliases.
   - Invoke `this.#options.setup?.(prog)`.
   - After setup, diff `prog.tree` keys to find:
     - **new command names** → record in a `Set<string>` `custom_commands` for later dispatch
     - **commands whose `handler` was reassigned** (override) → print a stderr warning: `Warning: custom command "X" overrides a built-in/tool command.`

4. **Dispatch step** (the `if (name === ...)` chain near the bottom of `run()`):
   - Keep existing branches for `tools`, `schema`, `call`, and tool aliases.
   - **Add a fallback before the final `this.#exit()`**: if `custom_commands.has(name)` (or, more permissively, if the parsed result has a `handler` that isn't one of the no-op handlers we registered), call `await parsed.handler(...parsed.args)`. Wrap in try/catch so errors flow through the existing `catch` block.
   - Note: `parse(..., { lazy: true })` returns `{ args, name, handler }` — sade pushes the options object as the last element of `args`, which matches the user's expected sade action signature `(positionals..., options)`.

5. **Generic parameter for setup typing (optional polish)**: leave the existing `<TCustom>` generic; the setup option doesn't need to flow through it.

### `packages/transport-cli/src/internal.d.ts`

No changes required unless we want to export the `CliTransportOptions` type. Recommended: export it so users get type hints.

### `packages/transport-cli/README.md`

Add a short "Extending the CLI" section showing:

```js
const cli = new CliTransport(server, {
    setup: (prog) => {
        prog
            .version('1.2.3')
            .command('hello <name>', 'Say hi')
            .action((name) => {
                console.log(`Hello, ${name}!`);
            });
    },
});
await cli.run();
```

Mention that overriding built-ins (`tools`, `schema`, `call`) or tool aliases is allowed but logs a warning, and that custom actions run naturally through sade.

## Risks / Edge Cases

- `prog.tree` includes sade's internal keys `__all__` and `__default__` — filter these when snapshotting.
- Sade indexes commands by the leading positional token (e.g. `'schema'` not `'schema <tool>'`). Detection of overrides must use the same indexing — read directly from `prog.tree` rather than reconstructing names.
- If a user registers a command with `.action()` returning a Promise, we must `await` it during dispatch.
- The `extract_command_args` helper at the top of the file separates the trailing options bag — for custom commands we want to pass sade's natural argument shape (positionals + options as last arg). Since the lazy-parse `args` already includes the options object as the last element, calling `handler(...parsed.args)` is correct and matches what sade would do non-lazily.
