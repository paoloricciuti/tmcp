# Plan: Implement MCP Tasks in tmcp

## Overview

Implement the MCP Tasks specification (2025-11-25) in the tmcp package. Tasks are durable state machines that allow requestors to poll for results of long-running operations.

## Key Requirements from Specification

### Task Lifecycle

- Tasks have states: `working` → `input_required` / `completed` / `failed` / `cancelled`
- Task IDs must be unique, string-based, receiver-generated
- Tasks have TTL (time-to-live) for cleanup
- Tasks require `createdAt` and `lastUpdatedAt` ISO 8601 timestamps

### Capabilities (Server)

```json
{
	"capabilities": {
		"tasks": {
			"list": {}, // Optional: support tasks/list
			"cancel": {}, // Optional: support tasks/cancel
			"requests": {
				"tools": {
					"call": {} // Support task-augmented tools/call
				}
			}
		}
	}
}
```

### Capabilities (Client)

```json
{
	"capabilities": {
		"tasks": {
			"list": {},
			"cancel": {},
			"requests": {
				"sampling": { "createMessage": {} },
				"elicitation": { "create": {} }
			}
		}
	}
}
```

### Protocol Methods (Server as Receiver)

- `tasks/get` - Get task status
- `tasks/result` - Get final result (blocks until terminal)
- `tasks/list` - List tasks with pagination (if capability enabled)
- `tasks/cancel` - Cancel a task (if capability enabled)

### Protocol Methods (Server as Requestor)

- Server sends `sampling/createMessage` or `elicitation/create` with `task` param
- Server polls client via `tasks/get`, `tasks/result`, `tasks/cancel`

### Tool-Level Negotiation

Tools declare `execution.taskSupport`: `"required"`, `"optional"`, or `"forbidden"` (default)

### Notifications

- `notifications/tasks/status` - Optional notification on status changes

### Phase 3: Core Tasks Implementation (Server as Receiver)

**File: `packages/tmcp/src/index.js`**

1. **Task mutation events (fire-and-forget)**

    ```javascript
    // Single 'task' event for mutations - pass taskId + partial task data
    this.#event_target.dispatchEvent(
    	event('task', {
    		action: 'create' | 'update' | 'delete',
    		sessionId,
    		taskId,
    		task, // full task for create, partial for update, undefined for delete
    	}),
    );

    // Transport handles mutation events
    server.on('task', async ({ action, sessionId, taskId, task }) => {
    	switch (action) {
    		case 'create':
    			return info.createTask(sessionId, taskId, task);
    		case 'update':
    			return info.updateTask(sessionId, taskId, task); // partial update
    		case 'delete':
    			return info.deleteTask(sessionId, taskId);
    	}
    });
    ```

2. **Task read operations via `tasks` option**

    Transports pass `tasks` callbacks when calling `server.receive()` or via context:

    ```javascript
    // In context passed to server.receive()
    {
      sessionId,
      sessionInfo: { ... },
      tasks: {
        get: (taskId) => Promise<Task | undefined>,
        list: (cursor?) => Promise<{ tasks: Task[], nextCursor?: string }>,
      }
    }
    ```

    The server uses `this.ctx.tasks.get(taskId)` and `this.ctx.tasks.list(cursor)`
    to handle `tasks/get`, `tasks/list`, and `tasks/result` requests.

3. **Add `#init_tasks()` method** to register handlers:
    - `tasks/get` - Get task by ID, return current state
    - `tasks/result` - Block until terminal, return stored result
    - `tasks/list` - List tasks with pagination (if capability enabled)
    - `tasks/cancel` - Cancel task if not terminal (if capability enabled)

4. **Modify `tools/call` handler**:

    ```javascript
    // In tools/call handler:
    const has_task_param = params.task != null;
    const tool = this.#tools.get(name);
    const task_support = tool.execution?.taskSupport ?? 'forbidden';

    if (has_task_param) {
    	if (task_support === 'forbidden') {
    		throw new McpError(
    			-32601,
    			'Tool does not support task augmentation',
    		);
    	}
    	// Create task, execute in background, return CreateTaskResult
    } else {
    	if (task_support === 'required') {
    		throw new McpError(
    			-32600,
    			'Task augmentation required for this tool',
    		);
    	}
    	// Execute normally and return result
    }
    ```

5. **Add `#execute_tool_as_task()` method**:
    - Generate unique taskId (using sqids)
    - Create task with `working` status
    - Emit `task_create` event
    - Start async execution
    - On completion: update task status, store result
    - On error: set `failed` status with statusMessage
    - Support `input_required` via elicitation

6. **Add `#notify_task_status()` method**:

    ```javascript
    #notify_task_status(taskId, task) {
      this.#notify('notifications/tasks/status', {
        taskId,
        status: task.status,
        // ... other task fields
      });
    }
    ```

7. **Update `tools/list` response** to include `execution.taskSupport` if defined

**File: `packages/tmcp/src/index.js`**

    ```javascript

    ```

2. **Update `message()` method**:

    ```javascript
    async message(request, options = {}) {
      // Check if client supports tasks for sampling
      if (options.task && !this.#client_capabilities?.tasks?.requests?.sampling?.createMessage) {
        throw new McpError(-32602, "Client doesn't support task-augmented sampling");
      }

      if (options.task) {
        // Send with task param, handle CreateTaskResult response
        const result = await this.#client?.request('sampling/createMessage', {
          ...request,
          task: options.task
        });
        return { task: result.task, poll: () => this.#poll_client_task(result.task.taskId) };
      }
      // Normal non-task flow
    }
    ```

## Open Considerations

1. **TTL Cleanup Strategy**: Use `setTimeout` per task, or periodic cleanup sweep?
    - Recommendation: Periodic sweep (every 60s) to avoid many timers

2. **`tasks/result` Blocking**: Use Promise that resolves when task completes
    - Store resolve/reject functions in task data
    - Call resolve when task reaches terminal state

3. **Progress Integration**: Task progress via existing `progress()` method
    - Progress token from original request remains valid throughout task lifetime

4. **`input_required` Handling**: When tool needs elicitation during execution
    - Emit elicitation request with `io.modelcontextprotocol/related-task`
    - Set task status to `input_required`
    - Resume execution when elicitation response received
